# Предстоящие записи в истории посещений клиента

Дата: 2026-09-29

## Задача

В истории посещений клиента (`src/components/app/clients/clientDetail/history`) должны отображаться не только завершённые визиты, но и предстоящие записи.

## Как сейчас

История посещений (режим с фильтром) грузит `GET /users/:user_id/user_customers/:id/appointments?sort=asc` (`useGetUserCustomerAppointmentsQuery`).

На бэке (`slotter-back/app/controllers/api/v1/user_customers_controller.rb`, метод `appointments`) три ограничения:

1. **Только визиты.** Без параметра `status` применяется скоуп `Appointment.visited`: `completed / arrived / delayed`, а также неотмеченные `pending / confirmed`, если время записи уже прошло. Будущие записи туда не попадают по определению.
2. **Только последние 30 дней.** Фронт не передаёт `period`, а по умолчанию на бэке `last_30_days` (`UserCustomers::Period::DEFAULT_PERIOD`). Будущие даты отсекаются ещё и этим. Попутно: секции «За прошлые 3 месяца» и «Ранее» на фронте почти никогда не заполняются, потому что старше 30 дней бэк ничего не отдаёт.
3. **Только первая страница.** Ответ постраничный (`pagy`), а фронт дальше первой страницы не грузит.

На фронте группировка `groupAppointmentsByPeriod` рассчитана только на прошлое:
- запись на следующий месяц попадёт в «За прошлые 3 месяца» (проверка `isAfter(threeMonthsAgo)`);
- сегодняшняя будущая запись попадёт в «В этом месяце» вперемешку с визитами.

## Варианты

### А. Доработать бэк (рекомендуется)

Добавить в эндпоинт параметр, например `include_upcoming=true`:
- выборка = `visited` ИЛИ будущие `pre_visit` (`requested / pending / confirmed`, время ещё не прошло);
- для будущих записей не ограничивать период (или брать от сегодня и дальше).

Фронт делает один запрос и делит ответ на «предстоящие» и «прошедшие» по дате и времени относительно текущего момента.

- **Плюсы:** один запрос, логика «что такое визит» остаётся на бэке, нет дублей.
- **Минусы:** нужна небольшая задача на бэке.

### Б. Только фронт, два запроса

- Текущий запрос оставить для визитов.
- Второй запрос: `status=requested,pending,confirmed` + `period=custom` с сегодняшнего дня на год вперёд.
- Объединить и убрать дубли по `id`: сегодняшняя запись, время которой уже прошло, попадёт в оба запроса.

- **Плюсы:** без бэка, можно сделать сразу.
- **Минусы:** два запроса, дедупликация, своя пагинация у каждого, правило «визит или предстоящая» дублируется на фронте.

## Как показать на экране

- Сверху отдельная секция **«Предстоящие»**, по возрастанию даты (ближайшая первой).
- Ниже прошлые визиты секциями, как сейчас, но от новых к старым (сейчас сортировка `asc`).
- В карточке предстоящей записи показывать статус: «Ожидает» / «Подтверждена» / «Заявка», чтобы не путать с прошедшим визитом.
- Отменённые будущие записи не показывать (предложение).

## Что нужно решить

1. Бэк (вариант А) или только фронт (вариант Б)?
2. Заодно чинить ограничение в 30 дней и загрузку только первой страницы, чтобы «Ранее» показывало старые визиты? Предлагаем да: для истории посещений оба ограничения выглядят как ошибка.
3. Показывать ли отменённые будущие записи и заявки (`requested`)?
