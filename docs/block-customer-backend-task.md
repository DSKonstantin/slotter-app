# Бэкенд: блокировка клиента мастером

Дата: 2026-09-29

## Контекст

В карточке клиента (`src/components/app/clients/clientDetail/index.tsx`) кнопка «Удалить клиента» переименована в «Заблокировать клиента». Подтверждение:

> **Заблокировать клиента?**
> {имя клиента} будет заблокирован(а) без возможности повторной записи к вам

Сейчас кнопка вызывает `DELETE /api/v1/users/:user_id/user_customers/:id`, а он только удаляет связь (`@user_customer.destroy!`). Флага блокировки на бэке нет, поэтому текст обещает то, чего система не делает.

### Что происходит сейчас: кнопка удаляет клиента

**Что удаляется.** Только строка `UserCustomer`, а с ней имя клиента у мастера, заметка и категория (`customer_tag`). Других таблиц, ссылающихся на `user_customers`, нет.

**Что остаётся как было:**
- Все записи клиента, прошлые и будущие: `destroy` их не трогает. Будущие записи остаются активными, клиенту приходят напоминания, записи видны в календаре мастера, прошлые визиты учитываются в статистике.
- Чат: переписка остаётся у обоих, клиент может писать дальше.
- Согласия клиента (`consents`) и избранное.
- Уведомления, которые строятся по записям, а не по связи: «Запишитесь снова» (`Cron::RebookSuggestionsWorker`, `REBOOK_AFTER_CANCEL`) и просьба об отзыве (`Cron::ReviewRequestsWorker`).

**Что перестаёт работать (потому что связь удалена):**
- Клиент пропадает из списка клиентов мастера и из выбора клиента (`GET /customers`).
- Мастер пропадает из списка мастеров в приложении клиента (`customer_users`).
- Клиент выпадает из аудитории рассылок и не получает поздравление с днём рождения от этого мастера.

**Как связь возвращается сама** (через `UserCustomers::Addition`, уже без имени мастера, заметки и категории):
- клиент записался онлайн по ссылке — `BookingsController#create_appointment` его не проверяет;
- клиент добавил мастера в избранное;
- клиент создал чат с мастером (если чата ещё не было);
- мастер создал запись этому клиенту (`sync_customer_link`) — политика `customer_allowed?` это разрешает, если между ними есть чат;
- **одна из оставшихся будущих записей завершилась** (`Appointment#link_customer_to_user!`);
- мастер добавил клиента вручную или импортом контактов.

**Ещё что клиент может делать:** писать в чат, просить перенос записи, отменять и подтверждать свои записи.

## Задача

Заменить удаление клиента блокировкой. Мастер больше не удаляет клиента, а блокирует его: связь мастер–клиент сохраняется (вместе с именем, заметкой и категорией) и помечается как заблокированная, а все пути, которыми клиент может выйти на мастера, проверяют этот флаг.

### 1. Модель

- `user_customers.blocked_at :datetime, null: true` — по аналогии с `users.deactivated_at`, `customers.deactivated_at`, `consents.revoked_at`, `notifications.read_at`.
- Отдельный индекс не нужен: проверки идут по паре мастер–клиент (уже есть уникальный индекс `[user_id, customer_id]`), список клиентов — по `user_id` (индекс есть).
- Скоупы `blocked` / `unblocked` — по образцу `Notification.unread` (`read_at: nil`). Не `active`: у `Customer` уже есть `active` (`deactivated_at: nil`), а `UserCustomer` часто джойнится с `Customer`.
- Хелпер для проверок в контроллерах и воркерах — по образцу `Chat::Room.exists_between?(user_id:, customer_id:)`: `UserCustomer.blocked_between?(user_id:, customer_id:)`. Не называть его `blocked?`, чтобы не путать с проверкой у экземпляра (в коде такие проверки пишут как `blocked_at.present?`).
  docs/block-customer-backend-task.md 
### 2. API блокировки

Два варианта, выбор зависит от ответа на вопрос 1:

- **Отдельное действие** `PATCH /api/v1/users/:user_id/user_customers/:id/block` — если у блокировки есть побочные эффекты (отмена будущих записей, уведомления). Так же устроены действия записей (`confirm`, `cancel` и т. п.). `unblock` добавлять только вместе с разблокировкой в UI (вопрос 2).
- **Поле в существующем** `PATCH /api/v1/users/:user_id/user_customers/:id` (`blocked: true/false`) — если блокировка только флаг без побочных эффектов.

Переключатель (`toggle_block`) не делать: повтор запроса разблокирует клиента обратно.
- В `UserCustomerBlueprint` отдавать `blocked_at` (или `is_blocked`).
- Удаление клиента из приложения убирается: кнопка «Удалить клиента» заменена на «Заблокировать клиента», и фронт перестанет вызывать `DELETE`. Эндпоинт можно удалить или оставить только для админки.

### 3. Где проверять блокировку

| Точка входа | Что сейчас | Что нужно |
|---|---|---|
| `POST /book/:token/appointments` (`BookingsController#create_appointment`) | создаёт запись и связь | Главная точка. Клиент определяется по нормализованному телефону (`Customer.find_or_initialize_by(phone:)`); если он существует и заблокирован у мастера — отказ до создания записи, квот и согласий |
| `GET /users/:user_id/available_slots` с JWT клиента (приложение клиента) | отдаёт слоты | Пустой список или отказ (см. вопросы). Без JWT (веб-запись по ссылке) клиент неизвестен до ввода телефона, поэтому там блокировка срабатывает только при создании записи |
| `UserCustomers::Addition` | `find_or_create_by!` | Не снимать блокировку и не пересоздавать связь. Существующая заблокированная связь возвращается как есть |
| `POST /chat/rooms` от клиента | создаёт комнату (и связь через `Chat::Rooms::FindOrCreate` → `UserCustomers::Addition`) | Отказ, если клиент заблокирован у этого мастера |
| `POST /chat/rooms/:id/messages` от клиента | отправляет | Отказ (комната могла существовать до блокировки) |
| `PATCH /appointments/:id/customer_request_reschedule` | отправляет запрос мастеру | Отказ |
| `POST /favorites` на мастера | добавляет и создаёт связь | Решить: запрещать или разрешать без создания связи |
| Рассылки (`Marketing::Broadcasts::AudienceQuery`) | в аудиторию попадают все `UserCustomer` мастера | Исключать заблокированных |
| Поздравление с днём рождения (`Cron::BirthdayGreetingsWorker`) | берёт `customer.user_customers.first`, мастер может оказаться тем, кто заблокировал | Брать только незаблокированные связи |
| Список мастеров у клиента (`GET /customers/:id/customer_users`) | показывает все связи | Скрывать мастеров, заблокировавших клиента |
| «Запишитесь снова» по крону (`Cron::RebookSuggestionsWorker`, `REBOOK_SUGGESTION`) | уходит клиенту, если с последнего визита прошло `rebook_days_count` дней и новых записей нет | Не слать заблокированным — это прямое приглашение записаться |
| «Запишитесь снова» после отмены (`Appointments::NotifyEvent`, `REBOOK_AFTER_CANCEL` на `customer_cancelled` / `customer_declined`) | уходит | Не слать заблокированным. Иначе, если будущие записи при блокировке не отменяются, клиент отменит оставшуюся запись и получит приглашение записаться снова |
| Просьба оставить отзыв (`Cron::ReviewRequestsWorker`, `REVIEW_REQUEST`) | уходит после завершённого визита | Скорее всего, не слать заблокированным (решает продукт) |
| Уведомления по уже существующим записям (напоминание, подтверждение, отмена, перенос — `Appointments::NotifyEvent`) | уходят | Зависит от ответа на вопрос 1 |
| Действия клиента с уже существующей записью: отмена/подтверждение по токену (`/appointments/by_token/:public_token/cancel`, `confirm`), `customer_accept`, `customer_decline` | работают | Не блокировать: клиент должен иметь возможность отменить запись, которая у него осталась |

Проверено и блокировки не требует: Telegram/MAX-вебхуки (только привязка аккаунта, записи через бота нет), публичный профиль мастера `GET /users/:id` (публичные данные), `POST /users/quick_create` (создание мастера).

**Уведомления клиенту лучше закрыть в одном месте.** Все они идут через `Notifications::Create`, где уже определяется мастер-владелец (`gated_by` или `subject.user`) и получатель-клиент, и по настройкам мастера решается `deliver`. Проверку блокировки (`UserCustomer.blocked_between?`) можно поставить там: для `REBOOK_SUGGESTION`, `REBOOK_AFTER_CANCEL`, `REVIEW_REQUEST`, `BIRTHDAY_GREETING` не создавать уведомление вовсе, а для уведомлений по существующим записям поведение выбрать по ответу на вопрос 1. Так не придётся править каждый воркер отдельно, и новые виды уведомлений не обойдут блокировку. Нужно решить, создавать ли запись в ленте клиента при `deliver: false` (сейчас лента отражает событие всегда).

**Что меняется для мастера.** `CustomerPolicy#linked_master?` проверяет наличие `UserCustomer`. Сейчас после удаления мастер теряет доступ к данным клиента (`GET /customers/:id`, `visited_appointments`, `upcoming_appointments`). После блокировки связь остаётся, и доступ сохранится: история клиента остаётся видна мастеру.

Блокировка привязана к `Customer`, а он уникален по телефону. Другое имя в форме записи блокировку не обходит (имя у существующего клиента не перезаписывается), а другой номер телефона — обходит: это новый клиент. Это известное ограничение, решать его не нужно.

`UserCustomers::Addition` вызывается и при действиях мастера (`AppointmentsController#sync_customer_link`, `Appointment#link_customer_to_user!`, импорт контактов `Customers::Import::LinkCustomer`) — там связь тоже не должна пересоздаваться или разблокироваться.

Отдельно — ручное добавление клиента мастером (`POST /users/:user_id/user_customers`): он делает `find_or_initialize_by` и вернёт существующую заблокированную связь. Нужно решить: разблокировать (мастер сам добавил клиента заново) или вернуть связь с флагом блокировки, чтобы фронт показал «клиент заблокирован».

### 4. Ответ при отказе в онлайн-записи

Текст и код нужно согласовать, чтобы веб-запись показала понятное сообщение. Прямо сообщать клиенту «вас заблокировали», скорее всего, не стоит. Предложение:

```json
422 { "errors": { "base": ["Запись к этому мастеру недоступна"] } }
```

### 5. Список клиентов мастера

- `GET /users/:user_id/user_customers`: по умолчанию **скрывать** заблокированных или отдавать их с флагом, чтобы фронт показал бейдж? Решает продукт (см. вопросы).
- `GET /customers` от мастера (`current_user.customers.active`, выбор клиента при создании записи) — то же решение: скрывать или отдавать с флагом.
- Статистика (`user_customers/statistics`) считается по записям, а не по `UserCustomer`, поэтому блокировка на неё не влияет: прошлые визиты заблокированного клиента остаются в выручке и счётчиках. Менять не нужно.

## Вопросы продукту

1. **Будущие записи** заблокированного клиента: отменять автоматически (с уведомлением или без) или оставить мастеру решать вручную? Если отменять через обычную отмену мастером, клиенту уйдёт `APPOINTMENT_CANCELLED` (при `send_notification`) — нужно решить, допустимо ли это.
2. **Разблокировка**: нужна ли в приложении? Если да, где мастер видит заблокированных: фильтр в списке клиентов или отдельный раздел?
3. **Что видит клиент**: при онлайн-записи — ошибку «запись недоступна» после ввода телефона; в приложении клиента (где он авторизован) — ту же ошибку или сразу пустое расписание?
4. **Чат**: скрывать существующую переписку у клиента или только запретить новые сообщения?
5. **Мастер сам создаёт запись** заблокированному клиенту (`POST /users/:user_id/appointments`): запрещать или разрешать? Логично разрешить, ведь это решение мастера. Сейчас `AppointmentPolicy#customer_allowed?` пускает, если есть `UserCustomer` или чат; при блокировке связь сохраняется, так что без доработок запись будет разрешена. Если нужно запретить — проверку добавлять туда.

## Изменения на фронте после готовности бэка

- `handleDeleteCustomer` в `clientDetail/index.tsx` перевести с `deleteUserCustomer` на новую мутацию `blockUserCustomer` и сменить инвалидацию тегов.
- Типы `UserCustomer` в `api-types`: поле `blocked_at` / `is_blocked`.
- В зависимости от ответов на вопросы: бейдж или фильтр «Заблокированные» и кнопка «Разблокировать».
