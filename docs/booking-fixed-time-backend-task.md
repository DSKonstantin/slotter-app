# Бэкенд: фиксированное время онлайн-записи

Дата: 2026-09-29

## Бизнес-логика коротко

**Зачем.** Мастер хочет, чтобы клиенты записывались онлайн не на любое свободное время, а только на выбранные им времена. Например, только на 11:30, 13:00, 15:00, 18:00.

**Что настраивает мастер** (Аккаунт → Онлайн запись → Фиксированное время):
- **Тумблер** «Включить фиксированное время». Выключен — онлайн-запись работает как сейчас.
- **Режим:**
  - «Фиксированное» — один список времён на все рабочие дни;
  - «По дням недели» — мастер выбирает дни, в которые открыта онлайн-запись, и для каждого дня задаёт свой список времён.
- **Интервал сетки** — с каким шагом мастер выбирает времена. Тот же набор значений, что у «Шага записи» (5 мин … 4 ч), но это отдельная настройка.

**Что видит клиент при онлайн-записи:**
- Если тумблер выключен, всё работает как сейчас.
- В режиме «Фиксированное» клиенту в любой рабочий день предлагаются только времена из списка.
- В режиме «По дням недели» клиент может записаться только в выбранные дни и только на времена, заданные для этого дня. В остальные дни онлайн-записи нет.
- Время из списка показывается, только если оно свободно: не занято записью или перерывом, услуга целиком помещается в рабочий день и не наезжает на другую запись.
- Время вне рабочих часов в этот день просто не показывается.

**Правила:**
- Записаться онлайн можно только на разрешённое время, даже в обход интерфейса.
- Мастер сам может записать клиента на любое время, ограничение только для клиентов.
- Включение и выключение тумблера, смена режима и изменение графика не трогают уже созданные записи.
- Выключение тумблера или смена режима не стирают настройки: при возврате всё на месте. Работает только выбранный режим, второй список просто хранится.
- Нельзя включить фиксированное время с пустым списком: иначе клиентам некуда будет записаться.
- Если мастер меняет рабочие часы так, что часть времён оказывается вне графика, времена не удаляются, а просто перестают предлагаться клиентам.

**Календарь мастера.** Когда фиксированное время включено, мастер видит в календаре, куда к нему можно записаться онлайн. Это считает приложение, от бэка нужны только сами настройки.

**Нужно решить** (подробнее в разделе «Вопросы»):
1. Ограничивать ли время и для мастера (перенос записи, предложение времени в чате) или только для клиентов. Предлагаем только для клиентов.
2. «По дням недели»: день выбран, но времена для него не заданы. Клиент видит обычную сетку или в этот день записаться нельзя?

Ниже — технические детали.

## Как сейчас на бэке

**Где хранить.** Негде: полей и таблиц для фиксированного времени нет. Из настроек онлайн-записи в `users` есть только `appointment_step` (enum, значение = минуты: 5, 10, 15, 30, 60, 120, 180, 240) и поля согласий.

**Как считаются слоты.** `GET /api/v1/users/:user_id/available_slots` → `Appointments::AvailableSlots`:
- берёт `working_day` на дату (`working_days` хранятся по конкретным датам, не по дням недели), если его нет или `is_active = false`, возвращает `[]`;
- идёт от `working_day.start_at` до `end_at` с шагом `step`:
  - если переданы `service_id` / `service_ids`, шаг равен самой короткой услуге, а длительность записи — сумме услуг и допов (`for_services`);
  - иначе шаг берётся из `params[:step]` или `user.appointment_step`, длительность не учитывается;
- выкидывает прошедшее время сегодняшнего дня, пересечения с записями и перерывами, и слоты, после которых перерыв (`break_after_minutes`) накроет чужую запись.

Эндпоинт один на все роли: мастер (`current_user`), клиент (`current_customer`) и публичная страница записи `slotter-web` (шлёт `date_from`/`date_to` + `service_ids[]`).

**Проверка при записи.** `POST /api/v1/book/:token/appointments` (`BookingsController#create_appointment`) не сверяет `start_time` ни с сеткой, ни со списком доступных слотов. Модель `Appointment` проверяет только, что запись попадает в рабочие часы, не пересекается с записями и перерывами, и что перерыв после неё свободен. Поэтому клиент может записаться на любое время, если отправит запрос напрямую.

**Шаблон недели.** На бэке не хранится: рабочие дни создаются на конкретные даты (`POST /users/:user_id/working_days/bulk_create`). «Рабочих часов по дню недели» на бэке нет (см. вопрос 3).

## Задача

### 1. Хранение

Настройка одна на мастера, читается и сохраняется целиком, связей с другими таблицами нет. Подходят два варианта, выбор за бэком. Формат API (п. 2) от выбора не зависит.

**Вариант А: jsonb-колонка в `users`**

`users.booking_fixed_time :jsonb, default: {}, null: false`, по аналогии с `notification_settings` / `customer_notification_settings`.

- **Плюсы:** минимум кода — одна миграция, без новой модели. Приходит в `getMe` вместе с пользователем без `includes`.
- **Минусы:**
  - Прецедент подходит не полностью: `notification_settings` — плоские тумблеры `ключ → true/false`, а здесь режим, интервал, списки времён и списки по дням недели. Всю проверку (формат, дни, дубли, пустые списки) придётся писать руками, база ничего не гарантирует.
  - Логика «какие времена разрешены на эту дату» и валидации окажутся в `User` или рядом с ним, а модель и так большая.
  - Если по вопросу 3 бэк начнёт хранить шаблон недели, списки по дням недели логичнее держать рядом с ним, а не в jsonb в `users`.

**Вариант Б: отдельная таблица один к одному**

Как `subscription_membership` и `referral_code`: `has_one` у `User`.

```
booking_fixed_time_settings
  user_id      bigint, unique, not null
  enabled      boolean, default false
  mode         string    — fixed / weekly
  interval     integer   — минуты (5 … 240)
  fixed_times  integer[] — минуты от полуночи
  days         string[]  — mon … sun
  day_times    jsonb     — { "mon": [630, 750], ... }
```

- **Плюсы:**
  - Своя модель со своими валидациями и методом «разрешённые времена на дату», который используют расчёт слотов (п. 3) и проверка при записи (п. 4).
  - Типизированные колонки: интервал и времена — целые числа, дни — массив строк.
  - `User` не растёт, удобно смотреть и править в RailsAdmin.
  - Если появится шаблон недели (вопрос 3), модель легко связать с ним или расширить.
- **Минусы:** ещё одна модель и таблица, в `getMe` нужен `includes`, а в `PATCH /users/:id` вложенный объект придётся сохранять в связанную запись (`accepts_nested_attributes_for` или отдельный сервис).

**Предлагаю вариант Б**, особенно если по вопросу 3 решат хранить шаблон недели на бэке. Вариант А тоже рабочий, если важнее сделать быстро.

**В обоих вариантах:**
- Время хранить целыми минутами от полуночи (`690` = 11:30): их проще проверять, сортировать и сравнивать. Формат `"HH:MM"` нужен только в API.
- `fixed_times` и `day_times` хранятся одновременно. Когда мастер переключает режим, список другого режима не должен теряться.
- Если настроек нет (`{}` в варианте А, нет записи в варианте Б), фиксированное время считается выключенным и слоты считаются как сейчас.

### 2. API

Отдельный эндпоинт не нужен, достаточно существующего `PATCH /api/v1/users/:id`, как для `appointment_step` и согласий. Экран сохраняет всё одной кнопкой.

```
PATCH /api/v1/users/:id
{ "user": { "booking_fixed_time": { ...объект целиком... } } }
```

Формат объекта (в запросе и в ответе одинаковый, от способа хранения не зависит):

```json
{
  "enabled": true,
  "mode": "weekly",
  "interval": "thirty_minutes",
  "fixed_times": ["11:30", "13:00", "15:00", "18:00", "19:30"],
  "days": ["mon", "tue", "wed", "thu", "fri"],
  "day_times": {
    "mon": ["10:30", "12:30", "13:00", "14:30", "15:00"]
  }
}
```

- Время строкой `"HH:MM"`, как в ответе `available_slots` (`"14:00"`). Бэк переводит его в минуты при сохранении и обратно при отдаче.
- `interval` — отдельное от `users.appointment_step` значение, но в том же формате: ключ enum'а (`five_minutes` … `four_hours`), как `appointment_step` в `PATCH /users/:id`. Минуты — `User.appointment_steps[key]`. Мастер может выставить, например, шаг записи 1 ч и интервал сетки 30 мин, и наоборот.
- Дни недели: `mon tue wed thu fri sat sun`.
- Разрешить вложенный объект в `permit` (`booking_fixed_time: [:enabled, :mode, :interval, { fixed_times: [] }, { days: [] }, { day_times: { mon: [], tue: [], ... } }]`).
- Отдавать `booking_fixed_time` в `UserBlueprint` (view `:default`, чтобы пришло в `getMe`). Если настроек нет, отдавать `{}` или объект с дефолтами.
- В публичные view (`:public`, `BookingsController#show`) не отдавать. Клиенту нужны только готовые слоты.

**Валидация** (422 в формате `{ errors: { booking_fixed_time: [...] } }`):
- `mode` ∈ `fixed`, `weekly`;
- `interval` ∈ `User.appointment_steps.keys` (та же проверка, что для `appointment_step` в `UsersController`);
- каждое время — валидное `HH:MM` в пределах `00:00–23:55`, минуты кратны 5;
- ключи `days` / `day_times` — только из `mon..sun`;
- списки без дублей; порядок бэк может нормализовать сам (сортировка);
- лимит на длину списка (например, 288 = сутки с шагом 5), чтобы не прислали мусор;
- пустой список активного режима при `enabled: true` — см. п. 5.

Не проверять, что времена лежат внутри рабочих часов: `working_days` хранятся по датам и меняются. Время вне рабочего дня на конкретную дату просто не превращается в слот (см. п. 3).

### 3. Расчёт слотов

Если `booking_fixed_time.enabled` и расчёт идёт для онлайн-записи (см. вопрос 1), кандидаты берутся не из сетки `start_at + n * step`, а из списка:
- `mode = fixed` → `fixed_times` для любого активного рабочего дня, `days` не учитывается;
- `mode = weekly` → если день недели даты (`date.strftime("%a").downcase`) не входит в `days`, слотов нет (`[]`); иначе `day_times[day]`.

Каждый кандидат проходит те же проверки, что и сейчас в `build_slots`:
- внутри `working_day.start_at...end_at` (с учётом длительности, если она известна);
- не в прошлом для сегодняшнего дня;
- не пересекается с записями и перерывами;
- перерыв после записи (`break_after_minutes`) не накрывает чужую запись.

`step` и `service.duration` при этом на выбор времён не влияют, длительность нужна только для проверки «влезает ли запись».

Удобнее всего передать в `Appointments::AvailableSlots` опциональный `candidate_times:` и в `build_slots` итерировать по нему вместо `current += step`. Проверки останутся в одном месте.

Формат ответа `available_slots` не меняется (массив `"HH:MM"` или хэш по датам при `date_from`/`date_to`). Клиентов API менять не нужно.

### 4. Проверка при создании записи

В `BookingsController#create_appointment` (и в клиентском переносе записи, если он создаёт/двигает запись без мастера) при включённом фиксированном времени проверять, что `start_time` входит в разрешённый список для этой даты. Иначе:

```json
422 { "errors": { "start_time": ["время недоступно для онлайн-записи"] } }
```

Без этого фиксированное время ограничивает только то, что видно в интерфейсе, а прямым запросом можно записаться на любое время. Сейчас это вообще не проверяется (см. «Как сейчас»), так что заодно стоит сверять `start_time` с тем же `AvailableSlots`.

Проверку делать только при онлайн-создании записи и при переносе записи клиентом. В модельную валидацию на каждый `save` её не ставить: иначе старая запись на время вне списка упадёт с 422 при `confirm`, `arrive`, `complete` или при переносе мастером.

Записи, которые мастер создаёт сам (`POST /users/:user_id/appointments`), не ограничивать.

### 5. Что будет, если тумблер выключен (`enabled: false`)

Онлайн-запись работает так же, как до этой задачи. Настройки фиксированного времени при этом сохраняются.

- **Слоты.** `available_slots` считает их по обычной сетке: шаг по услугам, а без услуг — `step` или `appointment_step`. `mode`, `fixed_times`, `days` и `day_times` не учитываются.
- **Дни недели.** Ограничение по `days` в режиме «По дням недели» тоже не действует. Онлайн-запись открыта во все активные рабочие дни, как сейчас.
- **Создание записи.** Проверка из п. 4 не выполняется. Остаются только текущие проверки: рабочие часы, пересечения, перерывы.
- **Данные.** Выключение не очищает `mode`, `interval`, `fixed_times`, `days`, `day_times`. При повторном включении мастер получает прежнюю настройку. `PATCH` с `enabled: false` принимает и сохраняет объект целиком, как при `true`.
- **Существующие записи.** Выключение и включение не трогает уже созданные записи, даже если их время не входит в список фиксированных времён.
- **Валидация.** Если `enabled: false`, списки могут быть пустыми. Если `enabled: true`, а список текущего режима пустой (`fixed_times` в `fixed` или все `day_times` выбранных `days` в `weekly`), возвращать 422 `{ errors: { booking_fixed_time: ["выберите хотя бы одно время"] } }`. Для `weekly` это правило зависит от ответа на вопрос 2: если день без времён показывает обычную сетку, пустые `day_times` допустимы, а проверять надо только, что `days` не пустой.

Если мастер ещё ни разу не настраивал фиксированное время (настроек нет, см. п. 1), это то же, что `enabled: false`.

### 6. Режимы и сохранение

«Фиксированное» и «По дням недели» — одна функция с двумя способами задать список времён. В каждый момент работает только режим из `mode`. Тумблер `enabled` включает или выключает функцию целиком.

| `enabled` | `mode` | Что видит клиент |
|---|---|---|
| `false` | любой | обычная сетка, как сейчас |
| `true` | `fixed` | `fixed_times` в каждый активный рабочий день, `days` не учитывается |
| `true` | `weekly` | `day_times[день]`, только в дни из `days` |

**Сохранение:**
1. **Объект сохраняется целиком.** Приходят все поля (`enabled`, `mode`, `interval`, `fixed_times`, `days`, `day_times`), бэк сохраняет их как есть. Частичный merge не нужен.
2. **Неактивный список не стирается.** Мастер настроил «Фиксированное», переключился на «По дням недели» и сохранил: `fixed_times` остаются в базе, но не применяются. Когда он вернётся на «Фиксированное», прежний список будет на месте.
3. **Правки неактивного режима тоже сохраняются.** Если мастер поправил «Фиксированное», переключился на «По дням недели» и сохранил, в запросе придут оба списка с правками. Бэк сохраняет оба, работает только режим из `mode`.
4. **Проверка «список не пустой» — только для активного режима** (и только при `enabled: true`, см. п. 5). Пустой `fixed_times` при `mode: weekly` и пустые `day_times` при `mode: fixed` допустимы. Формат времён, дней и интервала (п. 2) проверяется для обоих списков.
5. **Интервал сетки общий для обоих режимов.** Все времена в обоих списках лежат на сетке интервала.
6. **Расчёт слотов и проверка при записи** (п. 3 и 4) смотрят только на `mode` и соответствующий ему список. Второй список для них не существует.
7. **Смена режима не трогает существующие записи**, как и тумблер.

### 7. Календарь мастера и изменение графика

В дневном календаре мастера приложение помечает свободное время, в которое онлайн-запись невозможна. Для бэка из этого следует:
- Отдельный эндпоинт не нужен. Приложение считает всё само из `booking_fixed_time` (из `getMe`) и данных рабочего дня, которые календарь уже загружает.
- В календаре окно онлайн-записи — от фиксированного времени длиной в интервал сетки. Бэк же для клиента проверяет, помещается ли услуга целиком (п. 3). Поэтому окно в календаре значит «время открыто для онлайн-записи», а не «влезет любая услуга». Это нормально, так и задумано.
- Кандидаты в слоты у бэка должны строиться из тех же данных (`mode`, `fixed_times`, `days`, `day_times`, рабочий день) и по тем же правилам, что описаны в п. 3 и 6. Иначе календарь покажет мастеру окно, которого клиент не увидит.

**Изменение графика.** Если мастер меняет рабочие часы так, что часть фиксированных времён оказывается вне рабочего дня, приложение предупреждает его при сохранении графика. Времена при этом не удаляются: в дни, где они не помещаются, они просто не становятся слотами. Если вернуть прежние часы, времена снова начнут предлагаться. На бэке для этого ничего дополнительно не нужно: так работает п. 3, где времена вне рабочих часов отбрасываются при расчёте, а не при сохранении.

## Вопросы

1. **Кого касается ограничение.** Предлагаю: только онлайн-запись клиента (JWT-scope customer и публичная страница без JWT). Мастер в своём календаре, при переносе записи и при предложении времени в чате видит обычную сетку по `step`. Или мастеру тоже показывать только фиксированные времена?
2. **Режим «По дням недели»: день выбран, а времена не заданы.** Показывать в этот день обычную сетку по `step` или не давать записаться вовсе? Второй вариант может быть понятнее мастеру: для дня не выбрано ни одного времени, значит, клиенты в этот день записаться не могут. От ответа зависит валидация в п. 5.
3. **Рабочие часы по дням недели.** На экране настроек мастер выбирает времена из сетки в пределах рабочего дня. Шаблона недели на бэке нет, есть только конкретные даты. Откуда брать часы для каждого дня недели? Варианты:
   - бэк хранит шаблон недели и отдаёт его;
   - бэк отдаёт «типичные» часы по дню недели, например по ближайшим будущим `working_days`;
   - приложение строит сетку на весь день (00:00–24:00) без привязки к графику, тогда от бэка ничего не нужно.
