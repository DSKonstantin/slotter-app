# Consents — согласия при онлайн-записи

---

## Архитектура

`consents` — факт подписания согласия клиентом для конкретного мастера.
Юридический артефакт: хранит снапшот текста на момент подписания, переживает
удаление клиента из CRM (`user_customers`), никогда не перезаписывается.

- Два вида (`kind`): `personal_data` (обработка ПД) и `marketing`
  (информационно-рекламная рассылка). Оба **необязательные**: отказ не мешает записаться
- Подпись привязана к редакции текста (`text_checksum`). Мастер сменил формулировку —
  прежняя подпись под новым документом не действует, клиенту предлагается подписать заново;
  старая подпись остаётся в истории со своей датой
- Отзыв — это `revoked_at`, а не удаление: юр. артефакт из базы не исчезает
- Уникальности в БД нет: одну действующую подпись на редакцию держит валидация модели
- Создаётся при онлайн-записи (`POST /book/:token/appointments`) и через клиентские ручки;
  ручное создание клиента мастером и импорт согласий не порождают

## Таблица `consents`

```
id              (bigint, PK)
user_id         (FK -> users, not null)      — мастер
customer_id     (FK -> customers, not null)  — клиент
kind            (string, not null)           — personal_data | marketing
text            (text, not null)             — снапшот подписанного текста
text_checksum   (string, not null)           — SHA256 подписанного текста = редакция
customer_name   (string, nullable)           — имя на момент подписания
customer_phone  (string, not null)           — телефон на момент подписания (E.164)
created_at      — момент подписания
revoked_at      (datetime, nullable)         — момент отзыва; NULL = действует
```

Индексы: `(user_id, customer_id, kind)` и `(customer_id)` — оба неуникальные.

## Настройки мастера (колонки `users`)

- `is_personal_data_consent_enabled` (boolean, default false) — тумблер «Запрашивать согласие у клиентов»
- `personal_data_consent_text` (text) — кастомный текст; пустой = стандартный шаблон
- `is_marketing_consent_enabled` (boolean, default false) — тумблер «Запрашивать согласие на рассылку»

Меняются через `PATCH /api/v1/users/:id` (`user{...}`), отдаются в `UserBlueprint :default`.
Стандартный шаблон: `Consents::StandardTemplate::PERSONAL_DATA_TEXT`, отдаётся мастеру в
`GET /api/v1/auth/show` → `resource.personal_data_consent_template` (кнопка «Применить стандартный шаблон»).

## Флоу клиента (виджет онлайн-записи)

1. `GET /api/v1/book/:token` → блок `consents`:
   `{ is_personal_data_consent_enabled, personal_data_consent_text (резолвнутый), is_marketing_consent_enabled }`
2. После ввода телефона: `GET /api/v1/book/:token/consents?phone=+79991234567`
   → `{ personal_data_signed: bool, marketing_signed: bool }` — показывать ли экран подписания.
   `true` означает «подписана актуальная редакция и не отозвана».
   Ошибки: 422 `{errors: {phone: ["обязательное поле" | "неверный формат номера"]}}`
3. `POST /api/v1/book/:token/appointments` с
   `appointment[consents][personal_data]` / `appointment[consents][marketing]` (booleans).
   - Согласия сохраняются только при явном `true` и только при включённом тумблере
   - Отказ или отсутствие параметров записи не мешают: `CONSENT_REQUIRED` не возвращается
   - Подпись ставится под текущую редакцию; повторная запись под той же редакцией дубля не создаёт

## Клиентские эндпоинты (JWT клиента)

- `GET /api/v1/customers/:customer_id/consents` — свои подписи по всем мастерам,
  постранично, свежие сверху. Каждая запись содержит мастера (`user`), `is_current` и `revoked_at`.
- `POST /api/v1/customers/:customer_id/consents` — подписать вне онлайн-записи.
  Параметры: `user_id` (мастер), `kind` (`personal_data` | `marketing`).
  Текст берётся с сервера — актуальная редакция мастера; клиент его не присылает.
  422, если вид неизвестен или мастер не запрашивает такое согласие.
- `POST /api/v1/customers/:customer_id/consents/:id/revoke` — отозвать. Строка остаётся
  в истории с `revoked_at`, повторный вызов идемпотентен. После отзыва можно подписать
  заново — появится новая строка, прежняя останется.

Отзыв согласия на обработку ПД фиксируется как факт: автоматического удаления данных
у мастера он не запускает, мастер видит статус в карточке и решает сам.

## Влияние согласия на рассылку

Рассылки удержания (`rebook_suggestion`, `rebook_after_cancel`, `birthday_greeting` — всё,
что помечено `stage: :retention` в `Notification::TOGGLES`) подчиняются двум правилам:

- мастер собирает согласия (`is_marketing_consent_enabled`) → нужна действующая подпись;
- мастер их не собирает → рассылки работают как прежде, по его настройкам уведомлений,
  **но клиенту, который явно отозвал согласие, не уходят никогда** — выключением тумблера
  волю клиента не обнулить.

Гейт стоит в `Notifications::Create`, поэтому его унаследуют и будущие массовые рассылки.
Лента клиента наполняется всегда — гейт снимает только внешнюю доставку (push/мессенджер).
Сервисные уведомления о записи согласием не гейтятся никогда.

## Карточка клиента (мастер)

`GET user_customers/:id`, `GET user_customers/card`, ответы `create`/`update` →
`user_customer.consents: [{ id, kind, text, customer_name, customer_phone, created_at, revoked_at, is_current }]`
(сортировка по подписанию). В `index` и в клиентском `customers/:id/customer_users` согласий нет.
Поле `is_current` показывает, действует ли подпись: `false` означает, что мастер менял текст
после подписания либо клиент отозвал согласие (тогда заполнено `revoked_at`).

## Скачивание PDF (только мастер)

`GET /api/v1/users/:user_id/consents/:id/download` (JWT мастера) →
attachment `consent_<kind>_<id>.pdf`: заголовок, текст согласия, клиент, телефон,
мастер, дата/время подписания (МСК). Генерация: `Consents::Pdf` (prawn + DejaVu).

## Вне скоупа (осознанно)

- Массовых рассылок как функции пока нет — гейт по согласию их дождётся в `Notifications::Create`.
- Скачивание PDF доступно только мастеру; в клиентском приложении его нет.
- Автоудаление данных при отзыве согласия на ПД не запускается — это продуктовое решение.
- IP подписания не фиксируется.
- Анонимной подписи по booking-токену нет: подпись ставится либо в момент записи, либо
  под JWT клиента — иначе кто угодно подписал бы согласие за чужой номер.
